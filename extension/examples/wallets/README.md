# Wallets example

Signing with a wallet key: tee-node generates the key inside a TEE and keeps it there, and the extension has it sign EVM transactions.
The wallet's project owner names one signer in the contract; the signer sends the transaction's fields, and the contract numbers it.
Each TEE holding the key builds the transaction, signs it and posts it to its proxy, ready to broadcast.

> [!WARNING]
> An example, not production custody.
> The key lives only in the memory of the TEEs holding it: a machine that restarts loses it, until it is restored from a backup.
> Whoever holds the signer's key has the TEE sign any transaction from the wallet, and the TEE checks nothing about the transaction beyond its chain id: no limits, no simulation.

## Layout

As the [template](../../template/README.md):

- `cmd/extension/main.go`: the entrypoint; it reaches the wallet keys through tee-node's sign port.
- `internal/app`: the op and its tests.
- `conformance/`: golden fixtures, generated by `internal/app/fixtures_test.go`.
- `contracts/`: the entrypoint contract, `InstructionSender`, with `setSigner`, `signTransaction` and `replaceTransaction`, its scripts and its forge tests.
- `Dockerfile`: the TEE image; it differs from the template's only in the lines after a `# per extension:` comment.

## Ops

| Op type | Op command | Channel | Payload | Result |
|---|---|---|---|---|
| `WALLETS` | `SIGN_TRANSACTION` | instruction | `abi.encode(bytes32 walletId, uint64 keyId, uint64 nonce, Transaction tx)` | the signed transaction: EIP-2718 bytes, ready for `eth_sendRawTransaction` |

`Transaction` is `(uint256 chainId, address to, uint256 value, bytes data, uint64 gas, uint256 maxFeePerGas, uint256 maxPriorityFeePerGas)`: an EIP-1559 transaction, but its nonce, with an empty access list.
`to` is always a recipient: the example doesn't create contracts.

The refusals, as `error: <text>` in the result's log:

| Text | When |
|---|---|
| `invalid payload` | the payload isn't exactly the contract's encoding |
| `chain id required` | `chainId` is 0 |
| `wallet key not on this TEE` | the TEE doesn't hold that key |
| `not an EVM signing key` | the key is another type, or signs with another algorithm, such as VRF |
| `cosigners differ from the wallet's` | the instruction's cosigners or threshold aren't the wallet's |
| `can't read the wallet key`, `can't sign` | tee-node failed, or the signature recovers to another address |

## Wallets

An extension's wallets belong to wallet projects, each with an owner, a key type and a signing algorithm.
A wallet holds keys, each generated inside one TEE of the extension by tee-node itself: the extension never sees the key, nor the instructions that create it.
It learns a wallet's id and key id only from its own payloads.

One key is one address, the same on every EVM chain.
So this example takes wallets of exactly one key: two would sign from two addresses.

## Who may sign

The wallet's project owner calls `setSigner(walletId, signer)`; the zero address stops it.
The signer calls `signTransaction(walletId, transaction)`, paying at least `quoteSignTransaction(walletId)`; the contract keeps any excess.
The contract refuses unless:

- the caller is the wallet's signer;
- the chain id isn't 0;
- the wallet's project is this extension's, with an `EVM` key that signs with `keccak256-secp256k1-ecdsa`;
- the wallet is in production, so not paused;
- the wallet has exactly one key, and a TEE in production holds it.

It sends the instruction to every TEE in production holding the key, as `receivingTeesAndKeys` lists them, with the wallet's cosigners.
The fee is per TEE: it rises when a restored key gains a holder.

## In the TEE

tee-node signs with any key the TEE holds, whatever the request, and checks only that an instruction's own cosigners signed it.
So the extension checks the rest itself, from the key's info at `GET /key-info/{walletId}/{keyId}`:

- the key is an `EVM` key that signs with `keccak256-secp256k1-ecdsa`;
- the instruction's cosigners and threshold are the wallet's, compared as tee-node compares them for its own wallet ops.

It then builds the transaction from the fields, has the key sign it through `POST /sign/{walletId}/{keyId}`, checks that the signature recovers to the key's address, and answers the signed transaction.
The key only ever signs an EIP-1559 transaction the extension built, never bytes a caller chose.

## Nonces

The contract numbers each wallet's transactions per chain, from 0: `nextNonce(walletId, chainId)` is the next.
Each chain counts the address's nonce on its own, so a wallet's first transaction on every chain is nonce 0.

Signing is deterministic: an instruction delivered again signs the same bytes, and the chain accepts that transaction once.
So the extension needs no replay protection, and keeps no state.

A numbered transaction that never lands blocks every later one on its chain: a lost instruction, a TEE that is down, a fee too low or a balance too short.
`replaceTransaction(walletId, nonce, transaction)` signs a nonce already numbered again, with any fields: to raise the fee of one still pending, or to replace one that never landed.
The counter only moves forward.
Both signed transactions stay valid, and public, until one of them lands.

## Broadcasting

The signed transaction lands on each TEE's proxy, at `GET /action/result/<instructionId>`.
Anyone may send it, with `eth_sendRawTransaction` or `cast publish`; the wallet's address pays the gas, so fund it on the target chain first.
The address is the key's: from `getWalletKeyPublicKey`, or recovered from any transaction it signed.

## Setting up a wallet

`fce` doesn't set up wallets yet; these are the on-chain steps, on the FlareTeeManager diamond:

1. The extension's owner, once: `addAllowedTeeWalletProjectOwners(extensionId, owners)` and `addSupportedKeyTypes(extensionId, ["EVM"])`.
2. An allowed owner: `createProject(extensionId, "EVM", "keccak256-secp256k1-ecdsa")`, then `createWallet(projectId)`.
3. `setAdmins(walletId, publicKeys, threshold)`, `confirmAdmin(walletId)` from each admin's address, optionally `setCosigners` and `confirmCosigner`, then `closeWalletInitialization(walletId)`.
4. `setMultisigThreshold(walletId, 1)`, and `addKey(teeId, walletId, claimBack)`, paying its fee: tee-node generates the key in that TEE.
5. Read the key's existence proof, signed by the TEE, from its proxy, and `confirmKey(proof, signature)`.
6. `enableWallet(walletId)`: the wallet is in production, and no key can be added any more.
7. On this contract: `setSigner(walletId, signer)`.

## Restarts

A TEE that restarts comes back as a new TEE, without its wallet keys.
tee-proxy backs each key up, in shares encrypted to the wallet's admins and to the data providers.
A restore puts the key on another TEE: from the shares, which needs the admins and the data providers, or directly from a TEE still holding it.
The project owner, or its backup manager, then confirms the new holder with `confirmKey`; until then, no instruction reaches it, and with no holder in production, `signTransaction` reverts with `ThresholdNotMet`.
A key that can't be restored is lost: no key can be added to an enabled wallet, so the way out is a new wallet, with a new address.

## Testing

```bash
go test ./examples/wallets/...                    # signing through a fake sign port, and the fixtures are current
go test ./examples/wallets/internal/app -update   # rewrite the fixtures after changing them
make test                                         # also runs the contract's forge tests
fce conformance ./examples/wallets                # build the binary and check it from the outside
fce image-check ./examples/wallets                # build the image, then check it from the outside
```

The fake sign port holds one wallet key: wallet `keccak256("fakenode wallet")`, key 0, no cosigners.
It is anvil's second test account, so the first fixture's transaction goes through on a local anvil:

```bash
anvil &
cast publish --rpc-url http://127.0.0.1:8545 "$(jq -r .result.data examples/wallets/conformance/1-sign-transfer.json)"
```

The unit tests decode each signed transaction and recover its sender; a stub sign port covers what the fake never answers, such as a VRF key or a signature from another key.
The forge tests send the fixtures' fields through the contract and check it builds the fixtures' payloads, so neither side can change the layout alone; they also cover the numbering, the replacement and each refusal.
