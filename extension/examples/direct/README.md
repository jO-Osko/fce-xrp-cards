# Direct example

Provisioning secrets through direct actions: authorized, safe to replay, and encrypted to the TEE.
An admin, set on-chain by the contract's owner, stores secrets in the TEE, such as an API key, through direct actions it signs.
The owner also runs hidden auctions in rounds: users bid through the contract, encrypted to the round's TEE, which names only the winner, signed for the contract.
Each TEE reports its admin as its state, which the contract checks for the registry.

Anyone who saw a direct action can post it again, at any later time.
So each direct action is either idempotent, as `PROVISION`, or protected against replay, as `ROTATE`.
[Direct actions](../../docs/direct-actions.md) explains why.

## Layout

As the [template](../../template/README.md):

- `cmd/extension/main.go`: the entrypoint; it fetches the TEE's address from tee-node, registers the ops and serves tee-node until stopped.
- `internal/app`: the ops, the state (the admin, the secrets, the rounds) and its report, and their tests.
- `conformance/`: golden fixtures, generated by `internal/app/fixtures_test.go`.
- `contracts/`: the entrypoint contract, `InstructionSender`, with `setAdmin` and the auction's functions, which is also the extension's state verifier, its scripts and its forge tests.
- `Dockerfile`: the TEE image; it differs from the template's only in the lines after a `# per extension:` comment.

## Ops

| Op type | Op command | Channel | Payload | Result |
|---|---|---|---|---|
| `SECRETS` | `SET_ADMIN` | instruction | `abi.encode(uint64 nonce, address admin)` | the same |
| `SECRETS` | `PROVISION` | direct | JSON `{"teeId", "name", "ciphertext", "signature"}` | JSON `{"name"}` |
| `SECRETS` | `ROTATE` | direct | JSON `{"teeId", "counter", "name", "ciphertext", "signature"}` | JSON `{"name", "counter"}` |
| `AUCTION` | `START` | instruction | `abi.encode(uint64 round)` | the same |
| `AUCTION` | `BID` | instruction | `abi.encode(uint64 round, uint64 number, address bidder, bytes ciphertext)` | `abi.encode(round, number, bidder, bool valid)` |
| `AUCTION` | `END` | instruction | `abi.encode(uint64 round, uint64 bids)` | `abi.encode(round, bids, address winner, uint256 amount, bytes signature)` |

The state lives in memory: the admin, the secrets, the last counter accepted from each admin, and for each round its leading bid and which bids it has seen.
A reboot wipes it, and the TEE comes back with a new key, so a new address, and a new registration.
Results and logs are public, so they never hold a secret.

### `SET_ADMIN`

The owner calls `InstructionSender.setAdmin(admin, teeIds)`, paying at least `quoteSetAdmin(teeIds)`; the contract keeps any excess.
It reaches each named TEE as an instruction; the zero address removes the admin.
Every TEE named must be in production: the platform reverts the whole call otherwise.
Only the owner can send it: the chain takes the extension's instructions only from its registered contract, and the op pair isn't served as a direct action.
Until it arrives, `PROVISION` and `ROTATE` answer `error: no admin`.

Each call takes the next number, `nonce`, from 1.
tee-node doesn't remember instructions, so the operator could deliver one again, or after a newer one, and set an old admin back.
The TEE applies only a `nonce` above the last it applied, and answers `error: nonce not above the last` otherwise.

### `PROVISION`

Stores a secret once.
The same secret again succeeds and changes nothing; another answers `error: provisioned with another value`.
Encryption is randomized, so the extension compares the decrypted secrets, not the ciphertexts.
A replay, whenever it comes, changes nothing, so `PROVISION` needs no counter.

### `ROTATE`

Replaces a provisioned secret.
Replayed later, an old rotation would set the secret back, so the admin numbers rotations: each `counter` must be above the last one this TEE accepted from that admin, or it answers `error: counter not above the last`.
Counters may skip; send rotations one at a time, in order.
Memory is enough: payloads signed before a reboot name the old address, which the new TEE refuses.

### Encrypting

The secret travels encrypted to the TEE's public key, which the TEE's proxy serves; `fce encrypt`, from the tooling repo, reads the secret from stdin:

```bash
key=$(curl -s "$PROXY_URL/info" | jq -c .teeInfo.publicKey)
ciphertext=$(printf %s "$SECRET" | fce encrypt -pubkey "$key" -tee "$TEE_ID")
```

`-tee` refuses a key that isn't the TEE's at `$TEE_ID`.
The extension decrypts through tee-node's sign port, and answers `error: can't decrypt` for a ciphertext the TEE's key can't open.

### Signing

Each payload names the TEE it is for, `teeId`, and the admin signs it with the Ethereum signed-message prefix, as `cast wallet sign` does:

| Op | The admin signs the keccak256 of |
|---|---|
| `PROVISION` | `abi.encode(bytes32 opType, bytes32 opCommand, address teeId, string name, bytes ciphertext)` |
| `ROTATE` | `abi.encode(bytes32 opType, bytes32 opCommand, address teeId, uint256 counter, string name, bytes ciphertext)` |

The op pair in the signed bytes keeps a signature for one op from authorizing another, and the ciphertext in them keeps anyone from swapping the secret.
The extension answers `error: not for this TEE` when `teeId` isn't its address, and `error: not signed by the admin` for any other signature.

With Foundry's `cast`:

```bash
digest=$(cast keccak $(cast abi-encode "f(bytes32,bytes32,address,string,bytes)" \
  $(cast format-bytes32-string SECRETS) $(cast format-bytes32-string PROVISION) \
  "$TEE_ID" api-key "$ciphertext"))
cast wallet sign --private-key "$ADMIN_KEY" "$digest"   # or --account, --ledger
```

The payload is then `{"teeId":"$TEE_ID","name":"api-key","ciphertext":"$ciphertext","signature":"<the signature>"}`, posted to the TEE's proxy as the [template](../../template/README.md#my_direct_command) shows, with the op type `SECRETS` and the op command `PROVISION`.
[`conformance/03-provision.json`](conformance/03-provision.json) holds one, signed by a public test key for the fake sign port's TEE.

### `START`

The owner starts a round: `InstructionSender.startRound(period)`, paying at least `quoteFee(OP_TYPE_AUCTION, OP_COMMAND_START)`; the contract keeps any excess.
The contract numbers rounds from 1, picks one of the extension's TEEs in production at random to run it, and takes bids for `period` seconds; `rounds(round)` gives the round's TEE and deadline.
Several rounds can be open at once, each with its own TEE and deadline.
The TEE answers `abi.encode(round)` on its proxy, which tells bidders the round's TEE is up before they encrypt to it.
Bids don't wait for it: instructions reach the TEE in the order their votes finalize, not the order the chain took them, so a bid can arrive first.

### `BID`

Anyone may bid until the deadline: `InstructionSender.bid(round, ciphertext)`, paying at least `quoteFee(OP_TYPE_AUCTION, OP_COMMAND_BID)`.
The caller is the bidder: the contract sends the round's TEE the caller's address with the ciphertext, and numbers the round's bids from 1.
The plaintext is JSON, with the round as a number and the amount in decimal, zero-padded to 78 digits, encrypted as [Encrypting](#encrypting) shows, to the key of the round's TEE:

```bash
printf -v amount '%78s' "$AMOUNT"; amount=${amount// /0}
printf '{"tag":"AUCTION_BID_V1","round":%d,"bidder":"%s","amount":"%s"}' "$ROUND" "$BIDDER" "$amount" \
  | fce encrypt -pubkey "$key" -tee "$TEE_ID"
```

`printf` and the substitution are shell builtins, so the amount stays out of the process list.
FlareTeeManager's `getActiveTeeMachines(extensionId)` lists the extension's TEEs and their proxies.

- The ciphertext stays on chain for good, where anyone can read it; only the round's TEE can open it, so the operator and the chain see who bids and when, never how much.
- A bid is valid when the TEE's key opens it, its tag, bidder and round match, and its amount is a `uint256` above 0, in exactly 78 decimal digits.
- The width is fixed because a ciphertext is as long as its plaintext, plus 113 bytes: a free-form amount would show its number of digits on chain.
- The plaintext names the bidder and the round, so a copy sent by anyone else, or in another round, is invalid.
- The tag keeps any other ciphertext to the TEE, such as the admin's secrets, from counting as a bid.
- The answer is `abi.encode(round, number, bidder, valid)`: results are public, so it says whether the bid is valid, never its amount, and a bidder can fix a mistake before the deadline.
- An invalid bid still counts as seen, so it can't keep the round from ending, but it never leads.
- A bidder may bid again, and every valid bid stands: the round's highest valid bid leads, so a bidder can raise, never lower.
  Ties go to the lower bid number.
- The TEE keeps only the leading bid, never a beaten one, and which bid numbers it has seen.
- If the sign port fails, the TEE answers an error and the bid stays unseen: counted as invalid, a valid bid would be dropped unnoticed.

### `END`

After the deadline, the owner ends the round: `InstructionSender.endRound(round)`, paying at least `quoteFee(OP_TYPE_AUCTION, OP_COMMAND_END)`.
The contract sends the round's TEE the number of bids it took, and the TEE answers only once it has the round's start and every one of those bids:

- `error: round not started`: the start hasn't arrived.
- `error: bid N missing`: bid N hasn't, because it is on its way, lost, or withheld by the operator.

So a withheld bid shows as a refusal, never as a result without it; the owner ends the round again once the bid arrives.
Then the TEE answers `abi.encode(round, bids, winner, amount, signature)`, the same every time: the highest valid bid, at its own amount, or a zero winner and amount without a valid bid.
It names only the winner and the winning amount, never a losing bid.
The signature is the TEE key's, over the keccak256 of `abi.encode(RESULT_TAG, round, keccak256(abi.encode(bids, winner, amount)))`, which `resultDigest` computes.

### Settling

Anyone may submit the end's answer, read from the TEE's proxy: `InstructionSender.submitResult(round, result)`.
The contract checks that the round's TEE signed it, that the TEE is still in production, and that the count of bids is its own, then records the winner and the amount in `rounds(round)`.

The contract moves no money beyond the fees: it records who won, and at what price.
Paying is left to the fork, and it isn't simple: a deposit is public, so one that covers the bid bounds it, and a fixed bond doesn't bind a winner to a higher price.

### Lost and stalled rounds

Even an honest operator's pipeline can lose an instruction, and a round ends only with its start and every bid:

- The owner sends a round's start again: `resendStart(round)`.
- Anyone sends bid N again, even after the deadline: `resendBid(round, N, bidder, ciphertext)`.
  The contract keeps a hash of each bid's bidder and ciphertext, so only the bid placed can be sent again.

A round can still stall:

- Its TEE reboots, with a new key and none of the round's bids.
  The old address can stay in production after the machine is gone: the chain takes its bids, and their fees, but nothing answers.
- Its TEE leaves production, also when suspended for falling behind on the admin, as [State](#state) describes: the contract can't send to it, nor accept its signature.
- The operator withholds a bid, the end or its answer.

The owner then cancels it: `cancelRound(round)`, before ending it, or once `RESULT_TIMEOUT`, 1 hour, has passed since its last end with no result submitted.
So the owner can't cancel a round as soon as its winner shows on the proxy: anyone has `RESULT_TIMEOUT` to submit it.
It is trusted to end each round, though, and can hold one open.
Each start, bid and end pays the fee, which is all that bounds how many rounds and bids a TEE keeps.

## State

`GET /state` reports `abi.encode(uint64 nonce, address admin)`, the last `setAdmin` the TEE applied, `(0, 0)` before any.
Its `stateVersion` is `SECRETS_STATE_V1`, right-padded to 32 bytes.
The secrets and the counters arrive by direct actions, which the chain never sees, so the report leaves them out: the chain can check only what it sent.
The rounds come from the chain, but the report leaves them out too: the contract keeps each round's count of bids, and the TEE signs its result over it.

Register `InstructionSender` as both the extension's instructions sender and its state verifier; `Deploy.s.sol` writes its address under both names.
At each availability check the registry asks it about the state the TEE reported, and it accepts only:

- a `(nonce, admin)` it sent that TEE, or `(0, 0)`;
- while every newer `setAdmin` sent to that TEE is at most `MAX_STATE_LAG`, 2 hours, old.

So an operator who withholds a `setAdmin` keeps the machine on the old admin for at most 2 hours: then it fails its availability checks, and anyone can suspend it.
2 hours covers the time between the TEE reporting its state and the proof reaching the chain, which the registry's challenge window bounds, plus delivery; change `MAX_STATE_LAG` if your chain's are longer.
A `setAdmin` lost on the way, with nobody at fault, has the same effect: send another before anyone suspends the machine, and it catches up.
A machine suspended this way can't come back, because the contract can't send to a machine out of production: relaunch it, as a new TEE, and set its admin again.

## A new contract version

The extension can move to a new contract version while its TEEs keep running, as [re-pointing](../../docs/contracts.md#5-lifecycle) describes, but this example doesn't handle it.
The new contract numbers `setAdmin` calls and rounds from 1 again, while each TEE keeps what the old one sent:

- The TEE refuses the new contract's `setAdmin` calls as old, and the new state verifier refuses the admin the TEE reports.
- Rounds of the same number mix in the TEE, and each contract takes the other's results.

Relaunch the TEEs after moving to a new contract version, or bind both to the contract, for example by adding its address to each payload and to the signed result.

## Testing

```bash
go test ./examples/direct/...                    # the handlers, and the fixtures are current
go test ./examples/direct/internal/app -update   # rewrite the fixtures after changing them
make test                                        # also runs the contract's forge tests
fce conformance ./examples/direct                # build the binary and check it from the outside
fce image-check ./examples/direct                # build the image, then check it from the outside
```

The fixtures run in name order in one process, so they are numbered: the admin is set before the admin actions.
`02-set-admin.json` gives `again`: conformance sends it again, so it checks an instruction delivered again is refused.
`11-set-admin-older.json` sends a `setAdmin` numbered at or below the last applied: refused, as one delivered after a newer one.
`05-rotate.json` gives `again`, the answer to every later send of the same message: conformance sends it again, so it checks the replay is refused.
`09-provision-replayed-after-rotate.json` sends `03-provision`'s message after the rotation: refused, so even a late replay changes nothing.
`12-bid-before-start.json` sends a bid before its round's start: counted.
`15-bid-copied.json` sends alice's bid as bob's, and `16-bid-not-a-bid.json` the admin's secret as a bid: both counted, as invalid.
`17-end-bid-missing.json` ends the round before its last bid arrived: refused.
`19-end.json` ends it, naming alice the winner, signed by the fake sign port's key; the forge tests submit that result to the contract.
`20-end-not-started.json` ends a round whose start never came: refused.
Their secrets and bids are encrypted to the fake sign port's key once, with `fce encrypt`, and kept as constants in the test: encryption is randomized, so encrypting again would change the fixtures.
The forge tests check the state verifier against each way a TEE can lag or misreport, and that it never reverts: a revert would block every availability check of the machine.
